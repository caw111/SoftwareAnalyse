# 学术成果分享平台需求分析

## 第1页 系统管理什么 谁使用系统

平台整合论文、专利、项目和获奖信息。两组依据相同需求开展分析，围绕成果数据、门户管理和公开查询建立对象与交互模型。

| 使用者 | 业务需求 | 必须明确的边界 |
| --- | --- | --- |
| 公众用户 | 查找成果、筛选人物机构、查看详情 | 只能读取当前允许公开的内容 |
| 科研人员 | 申请本人门户、确认成果贡献、维护个人信息 | 门户管理权与成果贡献分别确认 |
| 管理员或审核员 | 采集数据、治理冲突、审核申请 | 按对象权限操作，保留来源和决定依据 |

本次重点分析三条业务链：**采集入库、门户认领审核、检索请求处理**。每条链都需要明确输入、处理结果以及失败或并发时的行为。

## 第2页 从业务事实识别核心对象

对象划分依据是稳定身份、独立职责和需要保留的历史。学者可以先于账号存在，同一原文可以多次被采集，一项成果可以有多位贡献者。

| 业务对象 | 需要保存的数据 | 主要行为 |
| --- | --- | --- |
| 账号与学者 | 稳定ID、身份依据、角色或来源 | 校验资格，区分同名人物 |
| 规范成果 | 成果ID、类型、题名、数据版本、来源证据 | 校验后更新，解析合并后的规范身份 |
| 成果贡献 | 人员或机构、角色、署名机构、确认状态 | 确认贡献，撤销对应关系 |
| 认领申请 | 申请人、目标、材料版本、状态和理由 | 提交、补充、审核、撤回 |
| 来源与任务 | 原文版本、固定范围、处理结果、断点 | 记录观测，恢复处理，追踪更新 |

**模型对应：**1组使用Account、Work、Contribution、ClaimApplication、CollectionTask；2组对应User、AcademicOutcome、OutcomeContributor、PortalClaim、CrawlTask。名称不同的对象先按业务职责对应，不能直接视为不同需求。

## 第3页 类关系决定权限 贡献和统计口径

| 关键关系 | 业务约束 | 直接影响 |
| --- | --- | --- |
| 四类成果继承统一成果父类 | 共享公共身份，保留类型专属字段 | 统一展示，按类型校验标识和日期 |
| 成果关联贡献 | 每条贡献属于一个成果，一项成果可有多条贡献 | 保留多作者、多角色和单位贡献 |
| 账号管理学者门户 | 当前有效绑定在两端均至多一条 | 防止重复授予门户管理权 |
| 任务观测来源记录 | 同一原文可被多个任务再次观测 | 重复采集保留证据，不重复建成果 |

**专利案例：**一件申请对应公开文献和授权文献，申请级成果仍计1件。文献数量与成果数量分开。

**具体表达：**1组单列门户授权、贡献机构和采集观测，并以PublicRelease组合ReleaseEntry。2组在管理关联、贡献属性和任务观测关系中承载部分信息，并以成果组合贡献明细。组合表达业务归属，不能直接等同于物理级联删除。

## 第4页 采集入库怎样形成可信成果

管理员或调度器提交来源、固定窗口和规则配置，采集控制取得有效执行尝试后，组织获取、清洗、身份匹配和规范入库。

| 处理步骤 | 必须完成的业务动作 |
| --- | --- |
| 验证响应 | 区分有效数据、合法空页、访问受限和非数据网页 |
| 保留原文 | 保存来源键、checksum、原文引用和规则版本 |
| 清洗校验 | 规范展示值与比较键，保留未知值和字段证据 |
| 身份匹配 | 可信强标识一致且无冲突时创建或关联成果，弱证据进入复核 |
| 规范入库 | 保存成果、贡献、来源映射、更新记录及可靠后续工作 |

**归并案例：**两个来源提供同一合法DOI且无冲突，保留两份来源依据，形成一个规范成果。只有相似题名时保留候选，不直接自动合并。

1组由M主交互引用N清洗子交互，治理复核使用GovernanceReview。2组在主图读取、清洗和入库消息中表达这些步骤。两组都要求隔离、待复核有明确原因与计数，技术错误不得静默丢弃。

## 第5页 采集失败以后 怎样恢复且不重复

**案例：固定窗口有三页，第一页已提交，第二页解析失败。**

| 事件 | 分页断点cursor | 整窗成功水位 |
| --- | --- | --- |
| 第一页可靠提交 | 指向第二页 | 保持原值 |
| 第二页解析失败 | 保持第二页 | 保持原值 |
| 恢复后所有输入处理完成并校验 | 本窗结束 | 才可推进 |

相同原文版本可以复用，但未完成的处理必须继续。旧attempt失效以后，不能再写入或通过迟到回调推进成功水位。停止请求也要等执行器安全退出后才成为停止结果。

**提交边界：**1组的页断点与来源引用、观测及处理登记共同提交，规范入库另设事务；2组将分页断点与规范成果及后续登记共同提交。两种表达都必须保证断点之前的数据或待处理工作可靠存在。

现有模型在重试耗尽后的终态上仍有分歧：1组进入STOPPED，2组保持FAILED、人工放弃后才STOPPED。应按共同需求统一该规则。

配图：[1组停止重试子图](图件/1组/03b-停止重试子交互.png)、[2组采集时序图](图件/2组/02_数据采集入库时序图.png)。

## 第6页 门户认领从材料提交到审核决定

**前置条件：**申请人已登录且科研身份审核通过，目标门户存在。材料默认私有，只向本人及有权审核人员开放，手填ORCID仅提供核验线索。

| 业务步骤 | 处理结果 |
| --- | --- |
| 提交申请 | 检查身份、目标、证明完整性、本人重复申请和版本 |
| 读取审核材料 | 校验审核权限，读取当前材料及对象版本 |
| 要求补充 | 说明缺项，补交材料递增版本并重新检查 |
| 作出决定 | 批准建立管理绑定，驳回保存业务理由，合法撤回保留历史 |

外部验证超时保留可恢复状态，不自动认定为冒领；材料更新后，旧版本审核不能继续终审。门户批准不自动确认全部候选成果。

**状态表达：**1组用六个业务状态，将验证和审核占用作为过程或内部记录；2组另设待验证、验证中、审核中，共九状态。这是当前模型对相同业务过程的表达分歧，需要统一。

配图：[1组认领审核主图](图件/1组/05-门户认领审核时序图.png)、[2组认领审核时序图](图件/2组/03_门户认领审核时序图.png)。

## 第7页 批准与撤回竞争时 如何避免错误授权

批准必须在一个逻辑事务中共同完成：**申请通过、有效管理绑定、审核决定与审计记录**。提交时重新校验资格、权限、材料及对象版本，保证账号和门户双向有效唯一。

**起点：管理员与申请人都读到待审核，version=7。**

| 谁先提交 | 已提交事实 | 另一请求的结果 |
| --- | --- | --- |
| 本人撤回 | WITHDRAWN，version=8，无新授权 | 旧批准冲突失败，不创建授权 |
| 管理员批准 | APPROVED，version=8，管理绑定共同生效 | 旧撤回冲突失败，解绑另走授权撤销 |

冲突方读取当前真实状态，不能覆盖终审历史。通知在事务提交后发送，通知失败可以补发。

**模型落点：**1组由ClaimControl协调ClaimApplication、PortalAuthorization、ReviewRecord及审计；2组在批准消息中共同提交PortalClaim、管理绑定和更新记录。两组都需要版本检查及持久化唯一约束，审核占用不能代替并发控制。

配图：[1组原子授权与撤回子图](图件/1组/05a-认领原子授权与撤回子交互.png)、[2组认领审核时序图](图件/2组/03_门户认领审核时序图.png)。

## 第8页 检索条件怎样得到正确的结果集合

检索边界接收关键词、成果类型、人物、机构、领域和日期条件。跨维度AND，同维度通常OR，多人物查询明确all或any；同名先选人物ID。

**查询：作者A01在机构I01的成果。**

| 固定样例 | 贡献事实 | 是否命中 |
| --- | --- | --- |
| R01、R04、R07 | A01的贡献关联I01 | 命中，共3条 |
| R06 | A01关联I03，另一作者A03关联I01 | 不命中 |

不能分别判断“作品有A01”和“作品有I01”后将R06加入结果。机构条件必须沿指定人物的同一贡献匹配，当前任职也不能替代历史署名机构。

1组通过ContributionAffiliation关联类明确这条路径；2组在OutcomeContributor的署名机构及证据中表达，并在查询契约中约束同贡献语义。

日期按成果类型解释：项目默认资助年度，不能用立项年补齐；精确标识按类型定位，项目编号还需结合资助机构消歧。

## 第9页 检索列表 总数与详情怎样保持一致

首次查询固定公开release，后续分页和详情继续读取同版内容，同时重新执行当前权限判断。

| 一致性问题 | 具体处理 |
| --- | --- |
| 新版本R2发布，用户列表绑定R1 | 续页和详情仍读R1；R1失效则提示刷新，不静默换版 |
| 候选10条，其中3条不可见 | 先取得允许集合，再统一计算7条的列表、total和分面 |
| 实际total=3，每页2条 | 得到真实总数后判断页码，第3页越界 |
| 查询或读取失败 | 明确返回错误，不当作合法空集或拼接最新数据 |

1组在QX子交互中细化页码判断、同版条目读取和返回前权限复验，权限修订变化时作废本次结果并要求重试。2组主图通过固定release、实时权限与同版规范ID读取表达一致性契约。

公开版本需要从同一快照构建索引和统计，校验READY后切换。构建失败保留上一版本，不把“采集完成”直接当成“新数据已可检索”。

## 第10页 用具体场景核对需求是否落实到模型

| 需求规则 | 检查场景 | 模型应得到的结果 |
| --- | --- | --- |
| 幂等与来源保留 | 相同合法DOI来自两个来源，再重复采集 | 一个规范成果，来源及观测仍可追溯 |
| 失败恢复 | 第一页已提交，第二页解析失败 | 保留有效断点，整窗水位不提前推进 |
| 并发授权 | 管理员批准与本人撤回同时发生 | 最多一个合法提交，状态和管理绑定一致 |
| 同贡献检索 | 查询A01与I01，另有R06交叉关系 | 返回正确3条，R06不混入 |
| 版本与权限 | 旧版本失效或返回前权限发生变化 | 明确要求刷新或重试，不返回混版内容及旧计数 |

这些场景分别检查对象身份、关系约束、事务边界和异常路径。两组模型按同一组业务预期核对，发现的问题回写类图、时序和需求记录。

当前形成的是需求分析模型与设计走查，真实系统行为仍需在实现后验证。
