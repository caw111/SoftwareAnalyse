## 第04页 门户认领的主要分歧是验证与审核过程是否成为业务状态

| Group2九状态 | 本组六状态 |
| --- | --- |
| DRAFT、PENDING_VERIFICATION、VERIFYING、PENDING_REVIEW、UNDER_REVIEW、NEED_MORE_INFO、APPROVED、REJECTED、WITHDRAWN | DRAFT、PENDING_REVIEW、NEED_MORE_INFO、APPROVED、REJECTED、WITHDRAWN |

**本组采用规则**

- 有效提交后进入PENDING_REVIEW，材料不足进入NEED_MORE_INFO。
- 验证动作和可选审核占用由过程记录、材料版本及ReviewLease表达。
- APPROVED、REJECTED、WITHDRAWN保留终审历史，再申请创建新编号。

**场景：外部核验服务超时。** 本组保留当前DRAFT或NEED_MORE_INFO并允许恢复，不把技术故障当作REJECTED。Group2则可在其验证阶段记录等待或转人工核验。

## 第05页 采集流程共同强调可恢复 预算耗尽的终态需要统一

**共同原则：**重复采集保持幂等，失败不推进整窗成功水位，停止需要执行器确认，采集成功与公开发布分别记录。

| 同一个事件 | 本组当前v2.0 | Group2采用的v1.1 |
| --- | --- | --- |
| 全窗口处理成功 | SUCCEEDED | SUCCESS |
| 可恢复故障且有预算 | FAILED后安排RETRYING | FAILED后安排RETRYING |
| 重试预算耗尽 | STOPPED，保留耗尽原因与失败历史 | FAILED，取消自动调度 |
| 配置或访问条件等不可重试故障 | 保留FAILED，等待人工处置 | 保留FAILED，等待人工处置 |

**本轮采用当前v2.0。** 若以后改用Group2规则，必须同步修改SRS、状态图、时序图、接口枚举和验收场景。

## 第07页 账号 学者 门户与管理授权分别维护

| 对象 | 关键属性 | 主要行为 |
| --- | --- | --- |
| Account | accountId、researcherVerified、角色范围、version | 校验申请资格与对象权限 |
| Scholar | scholarId、姓名别名、外部标识、身份依据 | 保留可区分的人物及来源证据 |
| ScholarPortal | portalId、公开简介、附加说明、visibility、version | 展示成果，维护允许修改的个人信息 |
| PortalAuthorization | authorizationId、validFrom、validTo、撤销原因、version | 判断授权有效性，撤销并保留历史 |

**关联约束：**每位学者至多一个规范门户。一个账号至多管理一个当前有效门户，一个门户至多有一个当前有效管理账号，历史授权可以多条。

**业务例子：**平台先采集学者档案并展示公开门户，本人注册后仍需通过身份及门户审核，批准才产生管理权。

## 第08页 四类成果共享公共身份 专利保留三个层次

`Work`保存规范ID、题名证据、数据版本、可见性和合并去向，四个互斥子类保留类型专属信息。

| 子类 | 核心身份与日期 |
| --- | --- |
| Paper | 合法DOI及来源依据，出版日期区分print、online、issued |
| Patent | 司法辖区与申请号，授权依据及授权日期 |
| Project | 资助机构、批准号和计划范围，默认资助年度 |
| Award | 奖励体系、年度、项目编号，获奖个人或单位 |

**专利计数例子：**一件申请对应一份公开文献和一份授权文献，申请级成果数仍为1。PatentDocument保存文献，PatentFamily按来源与族口径组织成员。

## 第09页 人物与机构联合检索必须沿同一条贡献关系

Contribution关联一个Work，贡献主体为Scholar或Institution之一。角色保存在同一关系的roles集合中。

Affiliation表达学者任职历史。ContributionAffiliation表达某次成果贡献发生时的署名机构，二者分别维护。

| 固定样例 | 事实 | 查询“A01在I01的成果” |
| --- | --- | --- |
| R01、R04、R07 | A01的对应贡献关联I01 | 命中，共3条 |
| R06 | A01关联I03，另一位作者A03关联I01 | 不命中 |

**错误实现：**分别判断“作品中有A01”和“作品中有I01”，会把R06错误加入，得到4条。

**正确实现：**存在同一贡献c，同时满足c的学者为A01、该贡献机构包含I01。

## 第10页 原文版本 采集观测与来源映射各有职责

| 对象 | 保存内容 | 必须保证 |
| --- | --- | --- |
| DataSource | 来源标识、访问策略、配置版本、启用状态 | 任务固定来源与配置 |
| SourceRecord | 稳定来源键、checksum、原文引用、来源更新时间 | 已保存内容版本保持不变 |
| CollectionObservation | 观测时间、批次、解析与规则版本、处理结果 | 相同原文可多次出现，结果仍可追踪 |
| SourceMapping | 原文版本与规范成果或专利文献的关联及依据 | 目标类型互斥，变更保留历史 |

**幂等键：**SourceRecord采用`(source_id, source_key, checksum)`。

同一原文重复抓取可复用内容版本、登记新观测。若上次处理未完成，仍须继续处理，不能因为checksum相同而跳过。

## 第11页 采集入库分三次提交 完整窗口结束后才推进成功水位

| 消息阶段 | 处理内容 | 可靠提交边界 |
| --- | --- | --- |
| M01至M06 | 固定来源、窗口和规则版本，取得有效attempt | 登记任务与执行尝试 |
| M07至M12 | 读取并验证响应，保存原文版本 | 页事务共同登记来源引用、观测及处理工作、下一cursor |
| M13及N子交互 | 清洗、强标识匹配、规范数据写入 | 规范事务共同保存Work、贡献、映射、UpdateRecord和后续工作 |
| M15至M17 | 核对全窗输入及处理结果 | 成功事务共同提交SUCCEEDED与successWatermark |
| M20至M21 | 构建并校验索引和统计 | 另行发布公开版本 |

**恢复例子：**三页窗口的第一页已提交，第二页失败。重试从有效断点恢复，第一页保留，整窗successWatermark保持旧值。

## 第12页 清洗归并必须保留证据 所有输入都有明确处理结果

**处理顺序：**解析编码、实体解码、Unicode与空白处理、字段校验、比较键生成、受控词表映射。

| 证据或记录情况 | 处理结果 | 保留内容 |
| --- | --- | --- |
| 可信强标识一致且无冲突 | 创建或关联规范成果 | 原文、映射依据、字段证据与规则版本 |
| 同名、相似题名或强标识冲突 | 进入GovernanceReview | 候选、冲突及理由 |
| 无来源、空题名、未知类型等 | 明确隔离 | 原文引用、隔离原因和计数 |
| 解析或写入技术故障 | ERROR并进入失败处理 | 错误与待恢复工作 |

**约束：**模糊自动合并默认关闭。待复核或隔离可以作为有记录的结果，未处理ERROR或丢失页面会阻止整窗成功。

## 第13页 停止在安全边界生效 旧执行尝试不能推进任务

采集任务六状态：PENDING、RUNNING、SUCCEEDED、FAILED、RETRYING、STOPPED。

| 事件 | 处理规则 |
| --- | --- |
| 运行中请求停止 | 先保存stopRequested，执行器安全退出后进入STOPPED |
| 可恢复失败且预算充足 | FAILED后登记下次时间，进入RETRYING，再取得新attempt |
| 配置、访问条件或结构故障 | 保留FAILED，等待人工处理 |
| 预算耗尽或管理员终止 | 按当前基线进入STOPPED，保留原因与历史 |
| 旧attempt迟到写入或回调成功 | 拒绝变更，不能推进cursor或successWatermark |

停止与成功同时发生时，以事务提交时的状态、有效attempt和停止标志判断。已完成的终态返回真实结果。

## 第14页 门户认领先校验身份与材料 审核只处理有权访问的申请

**前置条件：**申请人已登录，科研身份审核通过，目标门户存在且可认领。手填ORCID仅作为核验线索。

| 消息 | 业务动作 |
| --- | --- |
| CL01至CL08 | 提交私有证明，检查资格、目标、重复申请与版本，有效提交进入PENDING_REVIEW |
| CL09至CL13 | 有权审核人打开申请，检查对象范围，读取当前材料和版本 |
| CL14至CL16 | 材料不足要求补充，证据不成立驳回，批准进入原子授权子交互 |
| CL17 | 本人补交新材料，有效重提后回PENDING_REVIEW |

重复请求只返回本人既有结果。证明材料只向本人及有权审核人开放，技术验证失败保留状态和恢复原因。

## 第15页 批准和授权共同提交 并发撤回最多一个操作成功

**批准事务必须共同完成：**申请进入APPROVED、创建PortalAuthorization、追加ReviewRecord、写入审计。

提交前复验当前申请与材料版本、审核权限、申请人资格，以及账号和门户两侧的有效授权唯一性。

| 管理员与申请人都读到version=7 | 提交结果 |
| --- | --- |
| 本人撤回先提交 | 当前状态WITHDRAWN，旧批准因状态或版本冲突失败 |
| 管理员批准先提交 | 当前状态APPROVED，普通撤回失败，解绑另走授权撤销 |

**实现约束：**版本检查与有效绑定唯一性必须进入事务或等价串行化机制。写授权或审计失败时整笔回滚，不能留下“已批准但无授权”的记录。

## 第16页 公开版本固定查询内容 业务变更可靠登记后再发布

| 对象 | 公开更新中的职责 |
| --- | --- |
| UpdateRecord | 保存变更依据、前后版本及后续工作登记，发布失败可恢复 |
| GovernanceReview | 保存数据冲突、证据和治理决定 |
| PublicRelease | 固定快照、分类、规则和数据范围，校验后标记READY并发布 |
| ReleaseEntry | 保存某公开版本中的成果、关系及来源快照 |

**发布顺序：**固定快照，构建索引与统计，校验计数和样例，标记READY，短事务切换公开版本指针。

索引构建失败时继续提供上一可用版本，采集任务的SUCCEEDED保持。列表、详情与统计读取同一release，权限按当前规则校验。
